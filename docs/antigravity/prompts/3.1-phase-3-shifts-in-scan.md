## Goal
Make a check-in follow the person's assigned shift **when the organization has shifts switched on and the person has a shift**, and behave **exactly as it does today in every other case**.

## The golden rule: nothing changes unless shifts are on
- When the organization's `shiftsEnabled` is false (the default), or the person has **no assignment for yesterday, today or tomorrow**, or **anything about shifts cannot be read**, the scan, the status check and the undo must behave **exactly as they do today**: the same reads, the same writes, the same responses. Show this with tests of the planner (below) and keep your diff to the legacy path to the smallest possible hooks.
- An optional emergency switch: if the environment variable `SHIFTS_DISABLED` is `"1"`, treat every organization as shifts-off. (Name only; document it in the PR. Do not edit `.env.example`.)

## Decisions that differ from the design note
1. **Read budget.** Firestore bills one read per document. When shifts are on, a scan may read up to **3 assignment documents** (yesterday, today, tomorrow, by deterministic id) **plus up to 3 summary documents** (those same three days), all in parallel, instead of today's single summary read. That is **at most 5 extra document reads in one round trip**, only for organizations with shifts on. Report the exact read count of each path in the PR.
2. **Lenient mode is not built in this phase.** The setting exists, but in this phase a scan outside the window is **refused (Strict)** whatever the mode says; log it as `scan.refused` with a field `lenientNotYet: true` when the organization's mode is `"lenient"`. A later phase (3b) will build Lenient properly. Do not guess at it.
3. **A refused scan writes a note** to a new collection `refused_scans` (a best-effort step; see below).

## 1. The pure planner: `src/lib/shift-scan.ts`
Relative imports ending in `.ts`; no Firebase; no `Date.now()`; no randomness. Import from `./shift-engine.ts`, `./daily-summary.ts`, `./attendance-day.ts`, `./attendance-today.ts` and `./shift-requests.ts` (for `ShiftSettings`). Export:

```ts
import type { ShiftAssignment, ShiftSnapshot, ShiftWindow } from "./shift-engine.ts";
import type { DailySummary } from "./daily-summary.ts";
import type { ShiftSettings } from "./shift-requests.ts";

/** The three days whose shifts can matter to a scan at this instant: yesterday, today, tomorrow (organization timezone), oldest first. */
export function candidateShiftDays(nowMs: number, timezone: string): string[]

export type ShiftScanPlan =
  | { kind: "legacy" }   // do exactly what the app does today
  | { kind: "shift"; shiftDay: string; shift: ShiftSnapshot; direction: "in" | "out"; late: boolean; earlyDeparture: boolean; prev: DailySummary | null; window: ShiftWindow }
  | { kind: "refuse"; reason: "too_early" | "too_late"; shiftDay: string; shift: ShiftSnapshot; window: ShiftWindow; message: string };

export function planShiftScan(input: {
  settings: ShiftSettings;          // from the kiosk cache entry
  disabled: boolean;                // the SHIFTS_DISABLED switch
  nowMs: number;
  timezone: string;
  assignments: readonly ShiftAssignment[];                  // those that exist, for candidateShiftDays; may be empty
  summaries: Readonly<Record<string, DailySummary | null>>; // keyed by day: the summary document for that shift day, or null
}): ShiftScanPlan
```
Behaviour:
- `legacy` when `disabled`, or `!settings.shiftsEnabled`, or there are no (valid) assignments, or the engine returns `unassigned`.
- Otherwise call the engine's `classifyScan` with `windowMinutes: settings.shiftWindowMinutes` and `states[day] = { lastType: summaries[day]?.lastEventType ?? null }` for each candidate day (a missing or null summary means `null`).
- `matched` → `shift` with `prev = summaries[shiftDay] ?? null`; copy the engine's `direction`, `late`, `earlyDeparture`, `window`.
- `outside` → `refuse` with `message = describeOutside(...)` from the engine. **The mode (strict or lenient) does not change the plan in this phase** (see decision 2).

Also export, for the status route:
```ts
export function planShiftStatus(input: { settings: ShiftSettings; disabled: boolean; nowMs: number; timezone: string; assignments: readonly ShiftAssignment[]; summaries: Readonly<Record<string, DailySummary | null>> }):
  | { kind: "legacy" }
  | { kind: "shift"; shiftDay: string; summary: DailySummary | null }
```
It picks the shift day the same way a scan at `nowMs` would (use the engine; for `outside` or `unassigned` return `legacy`), so the phone's "are you checked in" answer matches what the next scan will do. For a night worker at 06:30 with a Monday shift whose summary says `in`, it returns `shift` with Monday's summary.

And for the refused-scan note:
```ts
/** Deterministic id: one note per person, shift day, reason and 10-minute period, so retries and repeated tries cannot flood the list. */
export function refusedScanId(employeeId: string, shiftDay: string, reason: string, nowMs: number): string
```
(`${employeeId}_${shiftDay}_${reason}_${Math.floor(nowMs / 600000)}`.)

## 2. `daily-summary.ts`
Add optional fields to the summary: `shiftId?: string`, `shiftName?: string`, `shiftStart?: string | null`, `shiftEnd?: string | null`, and let `SummaryIdentity` carry the same optional values so that **the first scan of a shift day creates the summary with them**. Later scans keep them (the code already spreads `...prev`). Existing summaries without them keep working. **Firestore rejects fields whose value is `undefined`**, and a new summary is built by spreading the identity object, so only add these keys when there is a shift (never write `shiftId: undefined`); do the same for the event's `shiftId` in the route. Add tests (in `daily-summary.test.mjs`) for creation with a shift, for a later scan keeping it, for a summary with none, and that no key in the created summary is `undefined`.

## 4. The scan route (`scan.ts`)
Keep every existing step and response. Add shift handling around them:
1. Compute `const days = candidateShiftDays(now, orgTimezone)`.
2. **Only if** `kiosk.shifts.shiftsEnabled && process.env.SHIFTS_DISABLED !== "1"`: **before the transaction**, read the person's assignment documents for those three days in one call (`firestoreAdmin.getAll(...)` with ids `assignmentId(caller.uid, day)`; the uid comes from the verified token, never the request), wrapped in `try/catch` and a time limit of 800 ms (`Promise.race`). Any error or timeout means **legacy** and a `logEvent` with `scan.shift_fallback`. Keep only documents that exist and whose `orgId` equals the caller's organization; turn them into `ShiftAssignment` values (day and the stored `shift` snapshot; ignore damaged documents).
3. If there is at least one assignment, then **inside the transaction** read the summary documents for those three days with one `t.getAll(...)` (instead of the single summary read) and call `planShiftScan`. If there are none, run the legacy transaction unchanged.
4. `legacy`: today's code, unchanged.
5. `shift`: use `shiftDay` in place of `today` for **the summary document, the cooldown check, the event's `dayKey`, and the summary identity**; use the plan's `direction`, `late`, `earlyDeparture` instead of `nextTypeFromSummary` and `computeScanFlags`; add `shiftId` to the event document and put the shift fields into the summary identity. Everything else in the event and the response is unchanged.
6. `refuse`: **do not write the event or the summary.** Return **HTTP 400** with `{ error: plan.message }` (this exact sentence; the phone adds "Your check-in was not recorded."). Then, as a best-effort step that can never change the response: create `refused_scans/{refusedScanId(...)}` with `create` (ignore `ALREADY_EXISTS`), fields `orgId`, `managerId`, `employeeId`, `employeeName` (from the token), `at` (ISO), `reason`, `shiftId`, `shiftName`, `shiftStart`, `shiftEnd`, `opensAt` and `closesAt` (ISO), `locationId`. Log `scan.refused` with outcome `denied`.
7. A scan that is retried and already recorded must still answer with the original result (`replayOf` unchanged), including a shift scan.

## 7. Rules and indexes
Add this block to `firestore.rules`, just above the "Default Deny" catch-all (mark it clearly in the PR):
```
    // ---- Refused scans (a short note when a check-in was turned away) ----
    // Written by the server only (docs/SHIFTS-DESIGN.md). Not an attendance record.
    match /refused_scans/{noteId} {
      allow read: if inOrg(resource.data) && (
        isOrgAdmin() ||
        (isManager() && resource.data.managerId == request.auth.uid)
      );
      allow create, update, delete: if false;
    }
```
Add two indexes to `firestore.indexes.json`: `refused_scans (orgId ASC, at DESC)` and `refused_scans (orgId ASC, managerId ASC, at DESC)`.

## 8. Tests (`shift-scan.test.mjs`, plus the changes above)
Every rule gets a test, using Africa/Accra, Day 09:00 to 17:00 (grace 0) and Night 22:00 to 06:00 (grace 10), 2026-10-12 a Monday. **At least:**
- `candidateShiftDays`: the three days in order; across a month end; across a daylight-saving change in Europe/London.
- **Legacy** is returned for each of: `disabled`; `shiftsEnabled` false; no assignments; only assignments whose window does not contain the scan and none for today or yesterday.
- **Day shift:** first scan 08:55 → `in`, not late, `shiftDay` Monday, `prev` null. Same person at 09:05 with no summary → late. Second scan 17:02 with summary `lastEventType "in"` → `out`, not early; 16:30 → early.
- **Night shift:** Monday 21:55 → `in`, `shiftDay` Monday. Tuesday 06:05 with Monday's summary `in` and no Tuesday summary → `out`, `shiftDay` **Monday**, `prev` is Monday's summary, not late, not early.
- **Overlap:** Monday night and Tuesday day shift; Tuesday 07:30 with Monday summary `in` → Monday check-out; with Monday summary `out` → Tuesday check-in.
- **Refusal:** Monday 15:00 with only the Monday night shift → `refuse`, `too_early`, message exactly `Your shift starts at 22:00. Scanning opens at 20:00.`; Tuesday 10:00 → `too_late`, message exactly `Your shift ended at 06:00 and scanning closed at 08:00. Please speak to your manager.`
- **Lenient setting still refuses** (decision 2) and **window length** from settings is honoured (30 and 240).
- **A summary for a day with no assignment** does not affect which shift is chosen.
- `planShiftStatus`: night worker at 06:30 → Monday's summary; day worker mid-shift → today's; outside the window → `legacy`.
- `refusedScanId`: stable inside one 10-minute period, different across periods, reasons and days.
- **Undo still works for a shift scan** (a test that builds the stored event shape and the summary the way the route will, and checks the logic in `undo.ts` that finds the summary from the **event's `dayKey`** would find the same document: read `undo.ts` and write the test around `summaryDocId(employeeId, event.dayKey)`).
