## Goal
When an organization has shifts switched on, the **Today panel** and the **attendance register** use each person's assigned shift to decide who is expected, present, late, absent or simply not rostered. **When shifts are off, both behave exactly as they do today.**

## What you must know first (facts from reading the code)
1. The Today route loads **only today's** daily summaries. A night worker on a Monday shift who is still on site at 01:00 Tuesday has a **Monday** summary, so today's numbers wrongly call them "not arrived". The shift-aware path must also load **yesterday's** summaries.
2. Daily summaries are filed under the **shift day** (the day the shift started; phase 3), so the **week chart needs no change**: a night shift already lands on its start day. **Do not change `week.ts`**; prove with a test that a shift-day summary counts on its start day.
3. The existing Today numbers **never count approved leave** (`onLeave` is hard-coded to 0 in `buildTodayFromSummaries`) and ignore holidays. That is an existing gap. **Do not change the existing behaviour** when shifts are off. In the shift-aware path, leave and holidays **are** used (see rules).
4. Each shift assignment document carries a copy of the person's `managerId` from when it was assigned. The integrator will separately make future assignments follow a person who changes manager. For now, manager-scoped assignment reads use `managerId == the manager`; document in the PR that a person moved from another manager may have older assignments that a manager's view does not see.
5. The register builder today treats every weekday without a summary as absent and every weekend day as off. With shifts on, **assignments** decide that.

## The golden rule: nothing changes unless shifts are on
- When the organization's `shiftsEnabled` is false, or `SHIFTS_DISABLED` is `"1"`, or no assignment exists in the period, the two routes must produce **exactly today's response** by exactly today's code path, with **no extra reads**. Prove it with tests of the pure builders and keep the diff to those paths to minimal hooks.
- If loading shift data fails, **fall back to today's path** and log `attendance.shift_fallback` (outcome `error`, reason `read_error`); never fail the dashboard because of shifts.

## 2. The Today builder: `src/lib/shift-today.ts` (pure)
Relative imports ending in `.ts`; no Firebase; no `Date.now()`. Export:
```ts
export function buildTodayWithShifts(input: {
  summaries: DailySummary[];                       // yesterday's and today's, in scope
  recentEvents: RawEvent[];                        // as for buildTodayFromSummaries
  roster: RosterMember[];
  assignments: { employeeId: string; dayKey: string; shift: ShiftSnapshot }[]; // yesterday's and today's, in scope
  leaves: ReportLeave[];                           // approved leave in scope (any dates; filter in the function)
  holidays: string[];                              // the organization's holiday dates
  settings: ShiftSettings;
  timezone: string;
  now: number;
  eventLimit?: number;
  truncated?: boolean;
}): TodaySummaryData
```
It returns the **existing `TodaySummaryData` shape unchanged**. You may add only these optional fields: `counts.notRostered?: number` and `shiftsOn?: true`. The panel UI ignores them; **do not edit the UI**.

**Rules** (for each person on the roster; `today` = the organization's day for `now`, `yesterday` = the day before):
1. **Which shift counts for the panel right now.** The person's assignment for `today`, **unless** their assignment for `yesterday` is *still running*: the shift's window has not ended (`now <= shiftWindow(...).closesMs`) and either `now < endMs` **or** that day's summary says they are still checked in (`state === "in"`). In that case yesterday's shift is the relevant one. A yesterday shift that is over and closed is ignored.
2. **Status**, using the engine's `shiftDayStatus` with: `assignment` = the relevant one or null; `hasScan` = the relevant shift day has a summary with a first check-in; `onLeave` = the person has an **approved** leave request covering the relevant shift day (start and end dates inclusive; use the leave's `startDate`/`endDate` strings); `isHoliday` = the relevant shift day is in `holidays`; `absentAfterMinutes` default. With no relevant assignment use the **calendar `today`** for leave and holiday and the person's today summary for `hasScan` (a scan still wins).
3. **Counts:** `present` = people with status `present`; `onSite` = of those, the ones whose relevant summary has `state === "in"`; `late` = of those, the ones whose relevant summary has `late === true`; `onLeave` = people with status `on_leave`; `absent` = people with status `absent`; `notRostered` = people with status `not_rostered`; `wfh` = 0; **`expected` = present + expected + absent** (people who should be here; leave, holiday and not rostered are not expected; someone who scanned while on leave still counts as present and expected).
4. **Lists and averages:** `notArrived` = people whose status is `expected` or `absent` (sorted by name); `late` list, `onTimeRate` and `avgShift` are worked out from the **relevant shift-day summaries** of the people with status `present`, exactly as `buildTodayFromSummaries` does for today's summaries; the activity list comes from `recentEvents` unchanged. Reuse the existing helpers rather than copying their logic where you can.
5. A summary for someone **not on the roster** is ignored. A person with no valid assignment is `not_rostered` (or `on_leave` / `holiday` if those apply).
6. `dayKey` in the result is the calendar `today`; `generatedAt`, `timezone`, `truncated` as in the existing builder.

## 3. The Today route (`today.ts`)
Inside the existing cached loader, after `loadOrgContext`: if `context.shifts.shiftsEnabled && process.env.SHIFTS_DISABLED !== "1"`, then in parallel load summaries for `yesterday..today` (use `loadScopedSummaries(scope, yesterday, today, WEEK_SUMMARY_CAP)`), `loadShiftAssignments(scope, yesterday, today, SHIFT_ASSIGNMENT_CAP_TODAY)`, `loadScopedLeave(scope, "approved")` and `loadHolidayDays(scope.orgId)` (both exist in `report-data.server.ts`), plus the recent events as now. If there is **at least one assignment**, call `buildTodayWithShifts`; if there are none, or anything throws, use today's code unchanged (log the fallback only on a throw). If either read was truncated, set `truncated: true`. With shifts off, the loader must be byte-for-byte the current one.

## 4. The register
**`report-types.ts`:** add the status `"expected"` ("not yet due") to `RegisterStatus`. **`AttendanceRegisterReport.tsx` and `report-export.ts`:** add `expected` to every status map: label **"Not yet due"**, code **"E"**, a pale neutral cell (`bg-slate-50 text-slate-500`; PDF fill `[248, 250, 252]`). Nothing else on those screens changes.

**`report-data.ts`:** extend `buildAttendanceRegister`'s input with an **optional**
```ts
shifts?: { assignments: { employeeId: string; dayKey: string; shift: ShiftSnapshot }[]; nowMs: number }
```
When `shifts` is **absent**, the function is exactly as today. When present, decide each person-day like this (in this order):
1. a summary for the day → `present` (as today);
2. approved leave covers the day → `leave`;
3. the day is a holiday → `holiday`;
4. **no assignment for that person and day → `off`** (not rostered, whatever the weekday, including weekends);
5. an assignment exists, no summary: if the day is **before today** → `absent`; if it is **today or later** → use the engine's `shiftDayStatus` with `nowMs`: `expected` becomes `"expected"`, `absent` becomes `"absent"`; any day **after** today is `"expected"`.
Totals count `absent` only for `absent` days. The "former team member" rows (people who moved away) keep their current behaviour, except their blank days stay `other`.

**`register.ts`:** after loading the roster context, if shifts are on (and `SHIFTS_DISABLED` is not `"1"`): load `loadShiftAssignments(scope, range.from, range.to, SHIFT_ASSIGNMENT_CAP_RANGE)` in parallel with the existing reads, and pass `shifts: { assignments, nowMs: Date.now() }` **only if there is at least one assignment**; set `readTruncated` also when assignments were truncated. With shifts off, or on a thrown error (log `attendance.shift_fallback`), call the builder as today.

## 5. Tests
**`shift-today.test.mjs`** (Africa/Accra; Monday 2026-10-12; Day 09:00 to 17:00 grace 0 and Night 22:00 to 06:00). Include at least:
- Day worker, scan at 08:55 → `present`, not late; at 09:30 with no scan → still `expected` (not absent yet); at 10:00 → `absent` (`absentAfter` 60); with `onLeave` → `on_leave` and not expected.
- **Night worker at Tuesday 01:00** with a Monday summary `state "in"` → `present` and `onSite`, **not** in `notArrived`; at Tuesday 06:30 with the Monday summary `out` and shift ended → no longer the relevant shift (their Tuesday assignment, if any, applies; if none, `not_rostered`); at Tuesday 07:30 with the Monday summary still `in` (the scanning window is open until 08:00) → still `present` and `onSite` on Monday's shift; at Tuesday 09:00 with the Monday summary still `in` (never checked out, window closed) → Monday's shift is **no longer relevant**: they are **not** counted on site, and their Tuesday assignment (if any) applies, otherwise `not_rostered`.
- A person with **no assignment** is `not_rostered`, is not counted as absent or expected, and is not listed in `notArrived`; counts add up: `expected = present + (expected-status) + absent`.
- Holiday today: rostered people with no scan are neither absent nor expected; a scan still shows `present`.
- Leave covers yesterday's night shift but not today → relevant-day logic uses the shift day.
- A summary for a non-roster person is ignored. Late list and `onTimeRate` come only from relevant, present people.
- **Shifts-off equivalence:** a test that `buildTodayFromSummaries` is untouched (call it with a fixed input and compare to a stored expected object), and a guard test that `today.ts` still contains the unchanged legacy call `buildTodayFromSummaries({ summaries, recentEvents, roster, timezone, now, truncated })`.
- Result shape: every key of the existing `TodaySummaryData` is present; the added optional fields are only `counts.notRostered` and `shiftsOn`.

**`shift-register.test.mjs`:** `buildAttendanceRegister` with no `shifts` gives **exactly** the existing output for a fixed input (compare to the same call as before); with `shifts`: unassigned weekday → `off`; unassigned weekend → `off`; assigned Saturday with no scan in the past → `absent`; assigned and scanned → `present`; leave beats assignment; holiday beats assignment; today before `start + 60` → `expected`; a future assigned day → `expected`; a night shift scanned yesterday shows `present` on its start day; totals ignore `expected` and `off`; the new status exists in the three status maps (read `report-export.ts` and the component and check `expected` is a key in each).
